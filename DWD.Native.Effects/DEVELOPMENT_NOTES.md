# DWD 开发备忘

> 当前目录是 2026-10-03 独立优化副本。最新结构、内存统计口径、异步调度及验证边界见
> `OPTIMIZATION_NOTES.md`。下文保留原版的开发沿革，旧的工作集数值不能直接与新版私有工作集比较。

## 当前版本定位

这是动态壁纸软件的当前主线版本，采用纯原生 Windows C++ 技术栈。旧的 WPF、libmpv 和外部 MPV 进程方案仅作为历史实验，不再是本项目依赖。

当前发布形态只有一个 `DWDNative.exe`。控制界面正常启动；同一个 EXE 使用 `--player` 参数进入后台壁纸播放模式，因此发布时不需要第二个播放器程序，也不需要附带第三方 DLL。

如果是为了学习代码，先阅读 `CODE_WALKTHROUGH.md`，再按其中的函数调用顺序对照源码中的中文注释。

## 技术架构

- `src/Controller.cpp`
  - 原生 Win32 控制窗口、壁纸库 UI、按钮和托盘菜单。
  - 扫描视频文件夹、异步生成封面、磁盘封面缓存。
  - 读取和写入 EXE 旁的 `DWDNative.ini`，不往注册表保存配置；跟随系统主题只读系统偏好。
  - 管理预览播放器和后台播放器进程，等待后台首帧就绪后再切换壁纸。
  - 判断高分辨率原片是否适合生成屏幕代理，并管理后台任务、缓存命中和自动交接。
  - 预览中的紫色取景框保存当前视频的归一化焦点位置，并传给后台播放器。
- `src/PreviewPlayer.cpp/.h`
  - 使用 Windows Media Foundation 的 MFPlay 播放当前选中视频。
  - MFPlay 实例在控制窗口可见期间常驻；切换视频时只异步创建并替换 MediaItem，不再销毁整条播放管线。
  - 每次切换携带递增代次，快速点击造成的过期回调会被丢弃。
  - 控制窗口打开时保持动态预览；最小化到托盘时释放预览解码，恢复窗口时重新打开。
- `src/SharedPreviewRenderer.cpp/.h`
  - 壁纸应用成功后释放前台 MFPlay，按名称打开后台播放器输出的 1280×720 D3D11 共享纹理。
  - 使用 Keyed Mutex 在两个进程之间同步，画面只在 GPU 内复制，不读回 CPU。
  - 后台有新预览帧时通过窗口消息通知前台，避免定时轮询；共享预览最多 30fps。
- `src/Player.cpp`
  - 使用 Media Foundation Source Reader 与 D3D11 Video Processor。
  - 视频只解码一次，再输出到每块显示器各自的交换链。
  - 每块屏幕按自身宽高比裁剪，可分别保存各屏主体焦点。
  - 壁纸窗口嵌入 WorkerW 桌面层。
  - 全屏应用或锁屏时立即暂停，持续 30 秒后释放解码器、双屏交换链和壁纸 HWND；系统挂起立即释放。
  - 隐藏协调窗口在深度休眠期间继续接收计时器、会话和电源消息；恢复时重建双屏窗口，首帧完成后才显示。
  - 同一条解码管线同时输出多屏壁纸和前台共享预览，前台不再重复解码已经应用的视频。
- `src/ProxyTranscoder.cpp/.h`
  - 同一个 EXE 的 `--proxy` 后台模式，使用 Media Foundation Transcode API 输出 H.264 MP4。
  - 允许 Windows 选择硬件转码器；不保留壁纸不需要的音轨，并响应控制器的取消事件。
  - 临时写入 `.part.mp4`，完整结束后才原子改名，避免把中断文件误当成可用缓存。
- `resources/app.rc`、`resources/app.ico`
  - EXE、标题栏、任务栏和托盘图标资源。
  - `app-icon.png` 是当前图标原始文件。

## 已处理的重要问题

- 主预览与右侧图库采用约 61.8% / 38.2% 的黄金分割；每页显示 6 张较大的 16:9 封面。
- 界面使用墨蓝画布、蓝灰卡片和独立头尾表面，旧版纯黑背景会自动迁移到新默认色。
- 双屏分别适配分辨率和比例，但保持单次硬件解码。
- 重复点击“应用到桌面”不会直接撤掉旧播放器；新播放器首帧准备好后才完成交接，避免随机黑屏。
- 退出程序时停止动态壁纸并通知 Windows 恢复原静态壁纸。
- 托盘图标从启动起常驻；标题栏叉号固定隐藏到托盘，不再显示关闭确认。正常退出只通过托盘右键“退出程序”。
- 主窗口标题统一为 `DWD`，用户界面不再暴露 Native、单解码、D3D11 等开发术语。
- 左下角设置入口使用项目内保存的 Line MD 矢量齿轮轮廓，并由 Windows GDI+ 以浮点坐标抗锯齿绘制；页码和视频数量留在图库末尾，运行状态独立放在底栏。
- 独立无边框悬浮球每秒汇总控制器、播放器和代理转码器的工作集，同时显示系统物理内存使用率与已用/总量；它不再依附主窗口，始终处于普通应用窗口上方，可拖动且双击恢复主窗口。
- 悬浮球不再使用 `SetWindowRgn + GDI Ellipse` 的整像素圆形裁切，改为 GDI+ 绘制 32 位 PARGB 位图并通过 `UpdateLayeredWindow` 做每像素透明合成；圆周透明度连续，解决高 DPI 下的锯齿。
- 使用时长统计由 `UsageTracker` 独立维护：`SetWinEventHook(EVENT_SYSTEM_FOREGROUND)` 监听前台切换，2 秒低频采样 `GetLastInputInfo` 判断空闲，锁屏状态通过 WTS 会话通知暂停。它不安装服务、不需要管理员权限，也不使用全局键盘/鼠标钩子。
- 每个应用同时累计活跃时长与观看时长：前者在 60 秒无输入后暂停，后者只在锁屏、休眠或长消息间隔时暂停。设置只切换展示口径，避免用户半天切换模式后混合统计。
- 使用记录按天写入程序旁 `UsageData/*.dwdusage`，V2 每行保存两个累计毫秒数，每 30 秒原子替换一次；除此之外只保存应用路径和显示名。统计窗口和托盘菜单只读取这份轻量聚合数据。
- 2026-09-28 在当前 Windows 11 上用管理员权限实测 `powercfg /srumutil`：官方导出是 E3 能耗采样，`Foreground/InteractivityState/TimeInMSec` 属于采样环境状态，同一时间可有多个应用被标记为 Focus，不能可靠还原每应用前台时长。因此未把它冒充历史使用记录；若以后补齐安装前历史，需单独验证并解析受保护的 SRUM App Timeline 表。
- 视频目录和缓存目录均记录在便携 INI 中，不写注册表。
- 新视频可通过右上角“刷新视频”立即重新扫描。
- 封面缓存固定为 320×180 BMP；高于屏幕很多的横屏原片可额外生成屏幕适配视频代理。
- 主预览一直使用视频；应用壁纸后不会退回静态封面。
- 不同比例视频可拖动取景框选择桌面裁剪时优先保留的主体位置。
- 缩略图采用按页虚拟化：只保留当前页、上一页和下一页的解压位图，其他封面仍留在磁盘缓存。
- 同一视频且取景位置未变化时重复应用，直接复用当前后台进程，不再创建第二个解码器。
- 主界面后备画布随窗口尺寸复用，鼠标悬停时不再反复创建整窗位图。

## 内存与性能约定

- 后台双屏播放只保留一条视频解码管线。
- 控制窗口预览的是“尚未应用的另一个视频”时，才会同时存在预览解码和壁纸解码。
- 壁纸应用成功后，控制窗口改用后台共享画面，因此稳定状态只有一条解码管线。
- 用户选择了尚未应用的另一个视频时，旧壁纸与新视频预览内容不同，会暂时存在两条解码；应用后重新合并为一条。
- 最小化到托盘后会释放预览解码，只保留壁纸解码。
- 封面在磁盘缓存，不会把完整视频读入内存。
- 点击封面后先显示缓存封面，并用 120 ms 合并连续点击；视频就绪后再无阻塞地接管画面。
- 缩略图线程使用 Windows 后台优先级，并在预览切换期间暂时让路。
- D3D11 Video Device/Context 在播放器启动时缓存一次；双屏 Present 使用非阻塞提交，避免不同刷新率的显示器串行等待垂直同步。
- 深度休眠保留很小的协调窗口和共享预览资源，销毁真正承载壁纸的双屏窗口，使 DWM 释放交换链；恢复时从暂停前时间点附近继续播放。
- 4K 等高分辨率原片首次应用后，后台生成不高于最大显示器物理分辨率的 H.264/30fps 代理；完成前原壁纸持续播放，完成后走首帧安全交接。以后前台预览和桌面播放都复用代理。
- 视频代理按文件大小与修改时间参与缓存键；换掉原视频后自动失效。缓存采用最近使用时间淘汰，总上限约 2GB。
- 推荐优先使用 H.264 MP4；其他格式是否能硬件解码取决于 Windows Media Foundation 和显卡驱动。
- 实测 3840×2160、60fps、约 30Mbps H.264：应用后的总工作集由约 1045MB 降至约 592MB；
  数值会随显卡驱动、屏幕数量、编码参考帧和视频规格变化。
- 2026-09-07 使用同一 4K 测试视频复测：后台播放器约 374MB 工作集 / 393MB 私有内存；
  隐藏控制窗口、应用成功并使用共享预览时，两进程合计约 414MB 工作集 / 422MB 私有内存。
  该数据用于同机回归，不等同于所有显卡和视频规格下的固定占用。
- 同机深度休眠联调：控制器与4K后台播放器总工作集从约 407.5MB 降到约 16.3MB；
  恢复后两个进程保持存活，共享预览和双屏输出重新建立。不同驱动下数值会有差异。
- 同机阶段七联调：3840×2160/60fps/约30Mbps 原片生成 2560×1440/30fps/约10Mbps 代理约需 13 秒，
  文件约 25.9MB；后台播放器稳定私有内存由约 588MB 降到约 330MB。首次生成期间转码进程会造成短时内存峰值，完成后自动退出。

## 便携配置

配置文件位于发布 EXE 同目录：`publish/DWDNative.ini`。

```ini
[Library]
WallpaperFolder=视频文件夹绝对路径

[Cache]
Directory=封面和优化视频缓存绝对路径
```

移动项目或发布目录后，应同步更新 `Directory`。缓存目录可以删除，程序会在需要时重新生成封面与优化视频。

## 构建

要求：Windows 10/11 x64、Visual Studio 2022 C++ 工具链、Windows SDK、CMake。

```powershell
cmake -S . -B build -G "Visual Studio 17 2022" -A x64
cmake --build build --config Release
```

构建输出：`build/Release/DWDNative.exe`。

日常开发只将 Release EXE 复制到 `publish/DWDNative.exe`，不维护多个历史压缩包。只有明确要求对外分享时才生成绿色 ZIP；绿色包不要包含个人的 INI 路径和 Cache 目录。

## 调试注意事项

- 不要强制结束控制进程来测试退出；强制结束可能绕过静态壁纸恢复逻辑。
- 调试“应用到桌面”时先看首帧 ready 事件，旧播放器应在新播放器 ready 后才停止。
- 修改 WorkerW 挂载或播放器交接代码后，必须验证：主屏、第二屏、重复应用、退出恢复、锁屏/全屏深度休眠与首帧恢复。
- 修改取景框时需要同时验证横屏视频、竖屏视频和两个不同比例的显示器。
- Windows 资源管理器可能缓存旧 EXE 图标；如果文件列表暂时显示旧图标，可重启资源管理器或复制为新文件名验证，资源本身不一定有问题。

# 2026-10-03：修复“显示运行中但未成为桌面壁纸”

现场日志确认：当前 Explorer 的 `Progman` 下有透明 `SHELLDLL_DefView` 和静态壁纸 `WorkerW` 子窗口。旧代码只查找顶层相邻 WorkerW，失败后退回 Progman，并把视频窗口放到 `HWND_BOTTOM`，因此被静态壁纸整层遮挡。此问题不是 MP4 解码失败，也不需要安装第三方播放器。

- 新 `WallpaperHost.h` 按实际结构查找：新版优先 Progman 子 WorkerW，旧版保留相邻顶层 WorkerW；检查 Explorer PID、可见性及虚拟桌面完整覆盖，拒绝隐藏小工具 WorkerW。未知结构不再假报应用成功。
- 双屏窗口用 `MapWindowPoints` 转换实际客户区坐标，尺寸完整创建后再交接。新壁纸放到壁纸宿主的顶部，不干扰其外面的图标层。
- 首帧提交不使用跳帧标志，普通帧仍非阻塞；桌面宿主销毁时仅重建 DWD 输出，不修改显示拓扑、不重置显卡/接口。
- 节能规则的“暂停”与“输出完全不可见”分开；仅一屏全屏时仍露出的壁纸保留最后一帧，不因 30 秒资源释放一起隐藏。
- `DWDNative.log` 为程序目录内最多约 1MB 的启动/挂载/错误诊断，不逐帧记录，不上传。`--exit` 是开发用优雅退出 IPC，与托盘退出走同一销毁流程；普通用户的退出入口仍是托盘。`--diagnose` 只记录桌面宿主结构。

验证：真实应用 P29（原始 1920×1080）和已有 2560×1440 适配视频；重复应用未新建播放器；双屏窗口几何 2560×1440、1920×1080 正确。只读桌面采样检测副屏 63 个露出点全部非黑且变化；暂停后变化为 0，恢复后再次变化；优雅退出后输出窗口为 0、静态画面不再变化。主屏在测试期间被其他应用覆盖，未将其视为已目视验证。未进行真实睡眠、接口断电或 Explorer 强制重启测试。

`build/Release/DWDWallpaperTests.exe` 是只读集成检测，不发布：默认检查至少一块露出桌面的画面变化；`--paused` 检查非黑静止；`--static` 检查无残留输出和静态画面。它不保存截图、不注入输入，覆盖的屏幕会报告 exposed=0。CTest 的宿主几何（含负坐标/双屏/小窗口）和使用记录两组测试通过。

最终 publish 再测：P29 首帧、两屏几何、实际副屏动态采样通过。点击叉号后控制窗口从窗口列表消失，播放器仍存续；超过 30 秒后再次采样副屏仍有 60/63 点变化、63/63 非黑，两个输出窗口未撤掉；再次打开 EXE 唤醒同一个控制窗口和播放器。已核对 build 与 publish 的程序 SHA256 一致，未生成 ZIP 或额外历史发布目录。

## 2026-10-03：预览/收回托盘回归补齐

用户随后报告预览卡顿、无法收起。重新启动后的现场测试未稳定复现永久卡死；代码检查发现并修正以下风险，不把它们宣称为已抓到的唯一现场原因：

- MFPlay/EVR 与共享纹理 DXGI flip swapchain 原来轮流绑定同一个 HWND。现在两个独立子窗口，同样的布局、互斥显示；共享窗口禁止 GDI 擦背景。Microsoft 的 flip model 指引明确不支持在同一 HWND 混用渲染 API。
- `PreviewPlayer` 的 UI 方法只投递命令；独立 MTA 媒体线程串行创建、切换、暂停和 Shutdown。回调仅入队；请求代次与播放器 epoch 同时检查，旧回调不能覆盖新选择。原生尺寸缓存后读取不调用 COM；第二个尺寸返回值是宽高比，不当像素使用。
- 收回托盘先隐藏主窗口及取景层，再异步停止 MF 预览。加载 12 秒未就绪时提供可重试错误，不永久显示载入中。析构最多等待媒体线程 2 秒；驱动不返回时状态独立存活，不引用已销毁的 UI。
- 共享画面的 Present 改成 DO_NOT_WAIT；KeyedMutex 除 S_OK 外（包括 abandoned）不复制。共享 D3D 的初始化/释放仍在 UI 线程，不声称已经消除所有驱动阻塞风险。

测试覆盖与边界见 `REGRESSION.md`。新增 `DWDPreviewTests` 仅在 build，传入两条视频路径及可选视频目录，不发布、不改原视频。保留正常的托盘退出交互；开发 `--exit` 仅用于同一销毁流程验证。
